# Phase 2 — セクター境界線表示（2-5）

## メタデータ

- **Status**: Deferred（後回し）
- **Date**: 2026-05-09

## 概要

レーダー画面に「訓練セクター境界線」を描画し、管制対象エリアの空間把握を改善する。`radarCanvas` の既存描画パイプラインに境界線レイヤーを追加し、将来のセクター別運用（ハンドオフ、責任区分表示）の土台を作る。

## 背景・課題

### 現状

- `Frontend/components/radarCanvas.tsx` は機体・レンジリング・ルート等を Canvas 描画している。
- 既存の設定 Context はレンジリング、データブロック、ベクトル表示が中心で、セクター境界の表示制御は存在しない。
- `spec/spec.md` の Phase 2-5 は未着手で、境界定義 JSON と描画方式の設計が次タスクとして明示されている。

### 課題（Problem Statement）

- 訓練中に空域の責任範囲が視覚化されず、インストラクション時の説明コストが高い。
- 将来の Phase 3-4（ハンドオフ）やマルチセクター化に先行して、座標定義と描画レイヤーを整理しておく必要がある。

### なぜ今か（Motivation）

公式空域データの整備コスト（AIS参照・手動正規化・更新追従）が想定より高いため、現時点では実装を後回しにする。先に既存機能の品質向上タスクを優先し、2-5 はデータ調達方針を固めてから再開する。

---

## 方針

### 決定方針（Decision）

1. **データ定義**: `Frontend/data/sectors/default.json` にセクター境界（ポリライン群）を定義する。初期版は固定データとし、読み込み失敗時は非表示でフェイルセーフ。
2. **描画レイヤー**: `routeRenderer.ts` か新規 `sectorRenderer.ts` に描画関数を分離し、`radarCanvas` から呼ぶ。描画順は「背景 → セクター境界 → ルート/機体」。
3. **表示設定**: 既存設定群と同様に `sectorBoundarySettingContext.tsx` を追加し、表示ON/OFFと線色を制御可能にする（初期値ON）。
4. **拡張準備**: 将来のセクター切替を見据え、定義は `id/name/segments` の最小スキーマで管理する。

### 検討した他案（Alternatives Considered）

- **案 A**: 境界線を `radarCanvas.tsx` に直書き。採用しなかった理由: 保守性が低く、将来のセクター追加時に差分が肥大化する。
- **案 B**: Backend API で境界を配信。採用しなかった理由: 今回は表示機能の最小実装が目的で、API追加はスコープ過大。

### トレードオフ（Trade-offs）

- **メリット**: 機能拡張に耐える構造で実装でき、表示品質を段階的に向上できる。
- **デメリット / 受容する制約**: 初期版は静的JSONのため、実運用の最新セクターと同期しない可能性がある。

## 調査メモ（2026-05-09）

- 公式一次情報は国交省系の `AIS JAPAN`（AIP配信）で管理される。
- 空域・管制区分の情報は AIP の `ENR 2` 系セクションに掲載される運用が一般的。
- 実務上は閲覧にアカウント登録が必要で、データは PDF/チャート中心のため、そのまま機械可読JSONとして取り込めない。
- そのため本タスクは「公式資料を参照してプロジェクト用JSONへ正規化する」前処理コストが高い。
- 結論として本スプリントでは 2-5 を Deferred とし、将来再開時に「出典管理・更新頻度・正規化手順」を先に合意する。
