# Phase 3 — ホールディング（3-2）

## メタデータ

- **Status**: Draft
- **Date**: 2026-05-09

## 概要

航空機に対して `HOLD` 指示を出し、指定 Fix 上空でホールディング（周回待機）を実行できるようにする。現在の「Direct To / Resume」は経路復帰には有効だが、到着調整・間隔調整に必須の待機操作が不足しているため、管制訓練シナリオの再現性を高める。

## 背景・課題

### 現状

- Frontend のオペレーター操作は `Direct To` / `Resume` が中心で、待機専用アクションがない。
- Backend には経路追従の基盤がある一方、ホールディング状態を明示的に保持・更新するフローが未整備。
- `spec/spec.md` では 3-2 が高優先度（🔴）かつ高難易度（★★★）の未着手項目になっている。

### 課題（Problem Statement）

- 到着流量を意図的に絞る操作ができず、運用上重要な訓練ケース（間隔調整・待機解除判断）を再現できない。
- レーダー上の挙動と操作意図が結びつかず、管制指示機能の拡張性が頭打ちになる。

### なぜ今か（Motivation）

3-1/3-1b（スクオーク）が進んだため、次は同じ Phase 3 の中核機能である 3-2 に着手するのが自然。3-2 は後続の高度制限（3-3）やハンドオフ（3-4）設計にも影響するため、早めに仕様を固定する価値が高い。

---

## 方針

### 決定方針（Decision）

1. **最小実用スコープ**: まずは「指定 Fix での標準待機」を提供し、軌道は **レーストラック型（直進→右旋回→直進→右旋回）** を採用する。円形ホールドは採用しない。
2. **API 契約先行**: `HOLD` 指示 API を先に定義し、Frontend はその契約に従って操作 UI を追加する。
3. **状態の明示化**: 航空機状態に `holding active / target fix` を保持し、解除は `RESUME` または専用解除指示で行う。
4. **表示整合**: レーダー上で「ホールディング中」であることが識別できる最小表示（データブロックまたはラベル記号）を入れる。
5. **高度制約の扱い**: 初期版ではホールディング専用の高度制約（maintain / at-or-above / at-or-below）は扱わず、3-3（高度制限指示）で対応する。
6. **同一Fixのトラック向き**: 侵入方向には依存させず、Fix名から決定論的に方位を生成して同一Fixで同一トラック向きを共有する。

### トレードオフ（Trade-offs）

- **メリット**: 管制操作としての実用性が上がり、シナリオ幅が広がる。
- **デメリット / 受容する制約**: 初期版は標準化された単純挙動に限定し、空港個別手順は扱わない。

## 完了条件（Success Criteria）

- [ ] `HOLD` 指示を API で受け付け、指定機がホールディング状態へ遷移する。
- [ ] ホールディング軌道がレーストラック型（直進→右旋回→直進→右旋回）である。
- [ ] 同一Fixで複数機にHOLDを指示した場合、侵入方向が異なっても平面トラック向きが一致する。
- [ ] ホールディング中の機体挙動が継続し、`RESUME` 指示で通常経路へ戻る。
- [ ] Frontend で HOLD 指示 UI が追加され、操作可能である。
- [ ] レーダー上で HOLD 状態が識別可能である（例: データブロックに `HLD` 表示）。
- [ ] 初期版で高度制約を追加しないこと（3-3で扱うこと）が仕様として明記されている。
- [ ] 既存の Direct To / Resume / Conflict 系機能に回帰不具合がない。

## 影響範囲

- **Backend/domain**: 飛行挙動、WaypointAction、航空機状態管理
- **Backend/application/interfaces**: 指示 API、DTO、ユースケース分岐
- **Frontend/components**: `flightPlanControl` など操作 UI
- **Frontend 描画**: データブロックまたは記号表示
- **README / spec**: 操作手順と API 契約の更新

---

## 実装計画

### Phase 1（契約と状態）

1. HOLD 指示 DTO / API を追加する。
2. 航空機に HOLD 状態を保持するドメイン表現を追加する。

### Phase 2（挙動）

1. 指定 Fix 周辺で待機軌道を継続する飛行ロジックを実装する。
2. RESUME で通常経路へ安全に復帰させる。

### Phase 3（UI と検証）

1. Frontend に HOLD 指示 UI を追加する。
2. HOLD 状態の可視化を追加する。
3. 単体/統合テストと手動シナリオ検証を行う。
